# UI standards (locked and proposed)

2026-10-31, moved into the repository 2026-11-02. Boards AA to AT in the "Heisenbug logo options" canvas. Locked means agreed with the owner and recorded here; proposed means drafted and awaiting a decision. Canonical copy lives in `heisenbug-design`; other repositories keep a synced copy.

## Locked

**Icons.** Lucide v1.66.0 (ISC licence), pinned. 66 icons in six groups (navigation, actions, reporting, direction, messages, editor); the exact names are in the pack's `manifest.json` (`heisenbug-icons-v1.1`, delivered in chat). Rules: 24 px grid, rendered at 16, 20 or 24 px only; 1.5 px rendered stroke at every size (viewBox stroke 2.25, 1.8 and 1.5); outline only; round caps and joins; `currentColor` in neutral text colours (red only for the open-bug dot); text label next to the icon by default; icon-only buttons need an aria-label and tooltip and a 36 px (desktop) or 44 px (phone) hit area; decorative icons are aria-hidden. The set is closed: add an icon by its Lucide name in a pull request with a reason. v1.1 (2026-10-31) adds `menu` for the phone menu on the landing page and docs (67 icons). Call-to-action links use `chevron-right`, external links `external-link`, Copy as prompt `message-square`. Not icons: the brand mark, status shapes, emoji, flags. A Flutter port of the set was not checked.

**Status shapes.** Six (the sixth, `notplanned`, was added 2026-10-31; see below), our own, 14 px grid, rendered at 14, 16 or 20 px, always with a text label nearby: `open` (filled disc, red), `in-progress` (ring, left half filled, amber), `fixed` (ring with check, green), `duplicate` (ring with slash, grey), `pending` (dashed ring, grey; label "Waiting"). Colours: light `#CF222E`, `#8A5300`, `#1D6B3A`, `#59606A`; dark `#F85149`, `#E3B341`, `#56D364`, `#9BA2AC`. All at least 4.8:1 against the ground. `notplanned` (ring with a level bar, grey, label "Not planned") closes the earlier gap; same ring, 14 px grid and 1.6 stroke as Duplicate, told apart by direction and always by its label (board AS). Issues close three ways, each with a required detail: Fixed (the release), Duplicate (the original issue), Not planned (a short reason). Who may close and whether reporters can reopen are decided below. A seventh state needs a design change. Status colours are used only for non-text status shapes with a text label: they must meet 4.5:1 against ground (house standard) and 3:1 against raised and selected (WCAG 1.4.11); status colours are never text colours, and red text uses the red-text tokens.

**Navigation.** Public site and app pages: one slim 48 px top bar (lockup, app switcher, section tabs, jump button with the command palette shortcut, notifications, Report a bug), a 28 px bottom status bar on desktop (shortcuts and list counts), and thread actions plus the reply box docked at the bottom of the thread pane. Developer dashboard: left sidebar. Phone: bottom bar with five items and a raised Report. SDK reporter sheet: no navigation. Rules: same order everywhere, current page marked, the palette is an addition and never the only route, no hover-only menus, skip link first.

**Colour.** Neutral by default. Light: ground `#F4F5F7`, raised `#ECEEF1`, selected `#E2E5E9`, hairline `#D3D7DD`, control border `#767B84`, text `#1F2125`, text 2 `#444A53`, text 3 `#59606A`, red text `#B71C27`, primary button `#1F2125` with a `#F4F5F7` label. Dark: ground `#1F2125`, raised `#25282D`, selected `#2D3137`, hairline `#353A41`, control border `#7E8590`, text `#ECEEF0`, text 2 `#B4BAC3`, text 3 `#9BA2AC`, red text `#FF6B63`, primary button `#ECEEF0` with a `#1F2125` label. No blue anywhere in the UI chrome.

**Fonts (decided 2026-10-31).** Product UI text is **Geist**. Data, code, issue numbers and the wordmark are **Spline Sans Mono**. Inter is no longer used anywhere. Both families are SIL Open Font License; self-host the files and do not load them from a third-party CDN.

**Responsive (decided 2026-10-31).** The website is mobile-first. Every board from now on includes a phone view at 390 px wide; tablet (about 768 px) and desktop (1280 px) are checked too. Rules: no horizontal page scroll at any width, 44 px touch targets on phone (24 px minimum anywhere), tables collapse to stacked rows, the phone navigation is the bottom bar from the navigation standard, forms and the thread reply box stay reachable above the on-screen keyboard, and text never relies on hover. Code blocks and tables scroll inside their own box, not the page.

**SDK reporter fonts (decided 2026-10-31).** The reporter inherits the host app's own font (web: `font-family: inherit`; Flutter: the app's `Theme` text styles). If inheritance fails or the host sets none, it falls back to the platform default font (`system-ui` on the web, the platform font in Flutter) rather than bundling Geist, which keeps the SDK small. A `fontFamily` option in the config overrides both. Layout must tolerate any font, so no fixed-width text boxes and no clipping. Colours, spacing and shapes stay ours; the Powered by badge keeps the wordmark font because it is an image.

**Theme (decided 2026-10-31).** The marketing landing page is dark only, with no switch. In the app (and docs), three choices under Appearance: **Dark** (the default), **Light** and **System**.
- A first-time visitor gets dark whatever their operating system says. System is something the user chooses, not the default.
- Store the choice in a first-party cookie (`hb-theme`: `dark`, `light` or `system`, one year) so the server renders the right theme in the first response. Signed-in users also keep it on their account.
- For `system`, a small inline script in `<head>`, before first paint, reads `prefers-color-scheme` and sets `data-theme` on `<html>`; a media-query listener follows later changes. This avoids a flash of the wrong theme.
- Tokens live in CSS variables under `:root[data-theme="dark"]` and `:root[data-theme="light"]`; set `color-scheme` to match so form controls and scrollbars follow.
- Public pages that are shared as images (link previews) are dark.
- The SDK reporter sheet follows the host app's theme, not this setting.
- Both themes must pass the same contrast checks (colour table above) and both are covered by the headless checks.

## Pages (boards AN to AR, and the holding page)

**Where the landing page lives (decided 2026-10-31).** The landing page goes live together with the whole platform and is built inside the main codebase, not as a separate site. Only the holding page is a separate static site. Check every claim on the landing page against what actually ships at launch when it is built.

**Landing page (AN desktop, AP phone; dark only).** Researched 2026-10-31: dev-tool pages that work lean on clean type, whitespace, a hero that matches product maturity, specific calls to action, and little salesy language; generic AI-looking pages share a hero formula, an icon-and-sentence feature grid and default gradients ([Evil Martians study](https://evilmartians.com/chronicles/we-studied-100-devtool-landing-pages-here-is-what-actually-works-in-2025), [Mindstudio on vibecoded pages](https://www.mindstudio.ai/blog/avoid-vibecoded-landing-pages)). Our rules: big type, hairlines and space instead of boxes, no feature grids, no lists in the body, one framed visual (the sample issue), no status dots used as decoration (shapes appear only with a label), no gradients, no invented numbers or logos. Structure: top bar, hero (the tagline as the headline: "Some bugs only happen to some people." with "Find out who." muted, 36 to 72 px), the sample issue with the observation strip and release rail, four statements with one small visual each (report, say you hit it too, know when it is fixed, hand it to your assistant), a section teaching the six status shapes in their standard colours with a word beside each (the generic icon set is deliberately not showcased, only what is unique to the platform), one closing call to action, and a footer. The landing page is dark only and has no theme switch (decided 2026-10-31); Dark, Light and System stay in the app's Appearance setting. All copy and the sample app (Lumen Notes) are placeholders; check claims against launch scope before shipping.

**Docs (AQ desktop, AR phone).** Same tokens, fonts and icons as the app. Desktop: left navigation with the current page marked by a bar and weight (not colour alone), a reading column of about 68 characters, and an On this page rail. Under 1180 px the rail becomes a collapsed dropdown; under 860 px the navigation moves behind a menu button. Code blocks have a language label and a Copy button; framework tabs (Web, Tauri, Flutter) persist across pages; callouts are neutral with an icon and a text label; each page has Copy as Markdown and Copy as prompt; a version switcher and search with the command palette. Code examples are marked as examples until the SDK API is final.

**Holding page (`apps/holding` in the platform repository).** One static site for traceway.dev and heisenbughq.com: "traceway.dev is now Heisenbug" with a link on the old domain, "Heisenbug is under development" on the new one, an Under development status line (in-progress shape, amber, labelled), a note that the old traceway.dev service is offline and its data was not moved, dark by default with Dark, Light and System, self-hosted fonts, a strict content security policy in `_headers`, no cookies and no third-party requests. No contact address until hello@ forwarding exists. Tested in a headless browser on both hostnames, both themes and at 390 and 1280 px.

**Naming the old project (decided 2026-10-31).** Public pages never use the bare name "Traceway", because another company (tracewayapp.com) uses it and people could confuse the two. The old project is always written as **traceway.dev**: footers read "formerly traceway.dev", and the holding page reads "traceway.dev is now Heisenbug". Internal documents may still use the old name.

## Motion (board AM)

CSS only, no animation library. Durations 80, 140 and 200 ms; easings `cubic-bezier(.2,0,0,1)` arriving and `cubic-bezier(.4,0,1,1)` leaving; travel 4 or 8 px; reduced motion sets travel to zero (fades stay) and stops loops and flashes. Nothing animates that is not in the catalogue on the board. Never: parallax, scroll-triggered reveals, hover lift on cards, bounce or spring, count-up numbers, animated gradients, route transitions. Checked in a headless browser: the menu travels 4 px over about 140 ms normally and 0 px with reduced motion; the pulse and flash animations are off under reduced motion. The live demos on the board show normal and reduced motion side by side and ignore the visitor's system setting (an earlier version used a toggle, which did not work for visitors whose system already asks for reduced motion, and clicks do not reach the page reliably inside the canvas).

## Markdown (board AL)

Raw Markdown is the stored form. Surfaces: title (140 characters, inline code only), bio (500, inline), reply (10,000, lists and quotes to 2 levels, code blocks, tasks, no headings or tables), issue and post (20,000, adds headings with h1 and h2 mapped to h3, and tables). No raw HTML, no images (attach through the uploader), no footnotes, no rules. Links http, https and mailto only; external links get `rel="nofollow ugc noopener noreferrer"`; link text that is a different address than the target shows the real address. Mentions, `#123` references and `//.` are added after sanitising. Reference pipeline: `md-reference.mjs` with tests in `md-reference-tests.mjs` (unified 11.0.5, remark-parse 11.0.0, remark-gfm 4.0.1, remark-rehype 11.1.2, rehype-sanitize 6.0.0, rehype-stringify 10.0.1; the tests import `./md-render.mjs`, so rename on use), to be placed in `platform/packages/markdown` in milestone M1. 43 of 43 hand-written cases pass. Hostile input at the size limit parses in 15 to 180 ms; a 5,000-level quote bomb took 550 ms, so render on write in a worker with a time limit. Not covered: a large XSS corpus or fuzzing, real browsers, the CSP. This is a working reference, not a security sign-off.

## Proposed: observations (board AK)

A report is an observation, not a post. Elements: Same here and Can't reproduce actions that attach version and device; a reproduction rate and run strip; a `heisenbug` label for issues that reproduce 10 to 90 percent of the time with 10 or more observers; a release rail (hollow worked, filled broken, dashed fix planned) that doubles as a crowd-sourced bisect; Follow renamed Break on with the events to stop at, alerts reading "Breakpoint hit"; issue numbers in a gutter; the SDK's recent actions as a captured trace. Compared with dev-null.sh (posts as commits with hash IDs, a feed called the Log, read from the site's text only), this borrows from the debugger and not from git.

**Votes versus observations (decided 2026-10-31).** A vote says "I care about this"; an observation says "I hit this, on this version and device, and it did or did not happen". On issues they are merged: **Same here** is the vote and carries the evidence at the same time (one per account per issue; version and device come from the SDK automatically, or from the browser on the web where it is optional; it can be withdrawn). **Can't reproduce** is evidence, never subtracted from the vote count, and needs a version and device. Default sort is "Most observed". Feature requests and replies keep plain up and down votes.

## Decided: Prompts, MCP and the no-hosted-AI rule (2026-10-31)

**Rule.** Heisenbug makes no AI model calls on its own platform: no auto-summaries, AI triage, "fix with AI", AI-written reports or embeddings-based duplicate detection at launch. Duplicate detection starts with Postgres text search. Checked against the Neon docs on 2026-10-31: `pg_trgm` 1.6, `unaccent` 1.1, `fuzzystrmatch` and pgvector 0.8 are all available (on Postgres 14 to 18), and built-in full-text search is part of Postgres itself, so no extension is needed for it. If hosted AI is ever added, it is a paid-tier or bring-your-own-key feature, using the per-organization metering already planned. Reason: cost grows per user on a free plan.

**In scope** (all assemble text from stored data; the user's own AI does the thinking):
- **Copy as prompt** on every issue: app, version, device, reproduction rate, release range, trace and similar issues, with variants (explain, write a failing test, suggest a fix). A preview shows exactly what will be copied.
- **SDK setup prompts** per framework (Flutter, Web, Tauri), generated from the live docs, plus `llms.txt` for the docs site. Placeholder APIs are marked as examples; the old SDK notes still use the Traceway names, so check the current SDK before any mock.
- **Read-only MCP server**: search issues, get an issue and its trace. Read-only, per-key rate limits, same metering as the public API, same fencing and redaction as the prompts.

**Decided 2026-10-31:** a neutral **Trace attached** badge and a "Has trace" filter (not a quality score; typed reports are never ranked down). The developer **Fix brief** (Copy as prompt over a group of duplicate issues) comes after launch as an extension of Copy as prompt. Boards: AT shows Copy as prompt with preview (desktop and phone sheet), the SDK setup prompt, the MCP connect screen and the safety rules.

**Safety rules for all of it.** Text written by other people is untrusted: in a generated prompt or MCP result it is fenced and labelled as data, never mixed with instructions. Secrets and personal data are redacted before anything is built (shares the trust and safety scanning milestone). Size limit on the output.

## Decided: closing and reopening issues (2026-10-31)

- **Who closes:** maintainers only (Owner and Maintainer roles). Reporters and the community cannot close an issue, but they can flag it.
- **How:** closing needs one of the three reasons (Fixed, Duplicate, Not planned) and a required detail, as in board AS. Duplicate links to the original; Fixed links to a release.
- **Reopening:** any signed-in account can reopen a closed issue by adding a fresh observation (Same here with a version and device) that shows it still happens. Reopening without new evidence is not offered.
- **If contested:** if a maintainer closes it again, a maintainer decides; the issue then stays closed until a maintainer reopens it, and further observations are still recorded and visible on it.
- **To settle when it is built:** whether the fresh observation must be on a newer version than the one the issue was closed on (suggested: yes for Fixed, no for Not planned), and how many reopenings are allowed before the issue is locked to maintainers.

## Checks run on the boards (2026-10-31)

Run in headless Chromium at 390 and 1280 px with axe-core 4.10 (WCAG 2 A and AA, 2.1 A and AA, best practice, ignoring the page-level rules that do not apply to a board), a Tab-key walk (names and visible focus rings) and a 44 px touch-target scan. Boards AE, AF, AI, AJ, AN, AQ and AT, and the phone boards AP, AR, AU and AV, pass with no violations. Fixes made as a result, and now rules for the real build:

- The lockup inside a link that already has a text label is `aria-hidden`; a lockup on its own gets the label "Heisenbug".
- Scrollable code blocks are focusable (`tabindex="0"`) and named.
- Links that go to another page (the framework switch in the docs) are a `nav` with `aria-current="page"`, not a `tablist`. Real tabs (the SDK switch in a dialog) use `role="tab"` with `aria-selected`.
- Heading levels never skip (the sample issue title is level 2 under the page's level 1).
- Interactive controls are at least 44 px in both directions on the phone, including the segmented controls.
- Not covered: a real screen reader, a real device, and the real artifact viewer (the check tool cannot load the canvas viewer because its bundle is larger than the file reader allows). Boards AB and AC (early direction explorations) have a few controls under 44 px and board AD is a fixed 1346 px layout of several phones, so none of those three is a responsive page; they are not being fixed.
- Phone boards now exist for the final views: AP (landing), AR (docs), AU (split view, dark) and AV (observations, dark). Light themes share the same markup and tokens, so they have no separate phone board.
